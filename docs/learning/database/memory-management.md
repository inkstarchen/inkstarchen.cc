
## 背景

数据库包含多个专属内存池

- 数据缓冲区：缓存磁盘数据页，减少物理IO操作加速SQL响应
- 日志缓冲区：数据库事务发生时，记录相关操作信息，合并、优化后批量写入磁盘，降低磁盘写入频率
- 数据字典缓存：包含表结构、表空间信息、索引定义等元素。数据库运行时频繁访问，防止每次从磁盘访问
- SQL计划缓存：缓存SQL执行计划，避免重复解析、计划生成与优化开销
- 全局存储过程缓存：存储编译后的存储过程、函数等对象，降低编译成本。

### 通常解决方案

- 预分配策略进行初始化，领域专家手调.
	- 静态、固定内存分配，对数据库工作负载的动态变化缺乏适应性.

### 场景示例

**高并发的事务处理场景**

- 系统对数据页的访问频率显著增加 -> 需要更大的缓冲池来存储热点数据

**复杂的分析型查询或决策支持场景**

- 系统频繁生成和优化执行计划，对计划缓存的需求上升

### 问题描述

**数据库自适应内存分配机制**

- 目标：根据各**缓冲区的实时使用情况**动态**调整各缓冲区内存分配**，以最大化系统整体的收益率(如命中率、QPS等)

#### 简化问题

**N个不同类型的缓冲区** 

**缓冲区属性**

- 唯一标识(`bufferId`)
- 内存约束: 下限`miniSize`,上限`maxSize`,实际分配内存`currentSize`
- 初始内存`initialSize`：即`currentSize`的初始值
- miss惩罚值`missPenalty`，每次未命中的性能损失量化值
- 置换策略`policy`：缓存满时的对象淘汰算法，默认提供`LRU`算法
- 动态设置：缓冲区的大小支持动态分配和回收，即提供接口实现，需要保证足够内存.

**系统约束**

- 系统总内存为`T`
- 所有缓冲区的`minSize`之和小于`T`
- 单个缓冲区的`maxSize`不超过`T`，但所有缓冲区的`maxSize`之和可以超过`T`

**程序输入**

- 同缓冲区相同对象的大小固定，输入中有保障

```
N T // 1 <= N <= 10, 2GB <= T <= 1024GB
// N lines following
bufferId| minSize  | maxSize  | initialSize | missPenalty |
0 - N-1 | 10KB - T | 10KB - T |             | 1 - 1000    |
M // 1 - 10000000 访问缓存请求序列长度
// M lines following
bufferId   |     objectId       | objectSize // 被访问对象的大小
目标缓冲区ID | 被访问对象的唯一标识 | 1 - 1048576 1字节到1M
```

#### 评估指标

**总惩罚值**

$$total\_penalty = \underset{0}{\overset{N-1}{\sum}}miss_i \times miss\_penalty_i$$

**算法运行时间**

$$total\_runtime(\mu s)$$

**取两者算法之和，越小排名越靠前**


$$estimation = total\_penalty + total\_runtime$$

#### 实现要求

- 修改置换策略（LRU）->（FIFO\LFU\CLOCK\...）
- 要求所有缓冲区必须严格实现对象访问过程中命中数量统计逻辑，命中计数存在逻辑错误或统计偏差，则判定无效
- 任何时刻所有缓冲区的内存占用总和不得超过总内存上限，单个缓冲区内存不得低于下限或超过上限
- 框架默认每处理500次请求触发一次内存分配调整。可设计动态调整策略(如根据系统负载、命中率变化或请求特征自适应调整频率),需要自行实现相关逻辑，确保调整机制不过度消耗系统资源，也能及时响应内存需求变化
- 需要自己实现内存动态调整策略，当总内存不足时，需设计合理的内存回收机制

#### 注意

- 不用考虑写回开销，只需要考虑置换的策略使得内存条件满足，数据ID能够被查询到

#### 必须要做的

- 缓冲区命中计数逻辑
- 内存超限检查

#### 我们可以做的改进和创新点

- 置换策略，如何保留下最有可能被继续访问的数据 | 操作逻辑判断？
- 内存动态调整策略 | 根据负载，命中率变化或请求特征自适应调整频率
	- 包含内存回收（回收的时机）

### 置换策略改进

**FIFO**效果差不考虑

**CLOCK算法**：FIFO的改进，给每个页一次保留的机会

**CLOCK算法改进**：**老化机制（Aging Mechanism）** 被引入以增强页面置换算法的历史感知能力|对持续活跃页面的偏好保留

**LFU算法**：每个页面计数，缺页时淘汰计数最小的

**LFU算法的改进**: 计数流失，不被使用则慢慢增大被置换的

当数据量大时维护开销大

**LRU算法改进**: 

- 提高加入新生代的代价(简单说就是，改进判断recent的标准，让更加长远数据留下来.)
- 现代LRU实现通常采用 **双向链表 + 哈希表**

**Mysql**的做法

对`old`区域额缓存进行第一次访问时，记录下这个访问时间

- 如果后续访问时间与第一次访问时间在某个时间间隔内，则该缓存页不会从old移动到young区域的头部，反之则移动到young区域的头部
- 这个间隔时间由`innodb_old_blocks_time`控制，默认为1000ms

> **思考**：LRU算法的基本思路就是，最近被用到的数据最有可能在后续的访问中被用到.但问题也一样存在，可以有很多一次访问的数据，挤占了那些在长时间来看被频繁使用的数据的空间.同时`LRU`需要维护一个链表，维护开销较大.

- **LRU**的性质很好，但是开销大，工程实践往往使用近似

#### Redis的内存淘汰策略

- 不进行数据淘汰 (不适用)
- 过期时间淘汰
	- volatile-random：随机淘汰设置了过期时间的值
	- volatile-ttl：优先淘汰更早过期的值
	- volatile-lru：淘汰过期时间中最久未使用的值
	- volatile-lfu：淘汰过期时间中最少使用的值
- 所有数据范围淘汰，即基础算法

**Redis对LRU算法的改进**

- 问题：链表带来的空间开销、访问数据后，进行链表移动的操作开销.
- 解决：添加字段记录数据最后一次访问时间。所有最后访问时间中，随机采样，淘汰最久没有使用的那个。

**Redis对LFU算法的改进**

- 问题：增加访问计数器的硬件成本、考虑次数但没考虑时间
- 解决：记录 访问频次（并非简单的次数，是根据访问时间来计算的）`logc(logistic Counter)`,和上一次访问时间`ldt(Last Decrement Time)`

> **思考**：过期时间提供了我们一个思路，即设置一个指标使得我们在淘汰数据时优先考虑这些数据项，而不需要对所有数据项进行考虑. 加入时间来维护数据项的淘汰指标.
